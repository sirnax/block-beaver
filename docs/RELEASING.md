# Releasing Block Beaver

Block Beaver uses semantic versions. The 0.4.0 package is public-ready (`private: false`), but preparing or tagging a candidate does not publish it to npm. The tag workflow publishes a GitHub source release only. Publication is a separate owner-authorized step.

1. Review a candidate pull request containing matching `package.json`/`package-lock.json` versions, a `## X.Y.Z — date` changelog entry, and compatibility notes. Generate the notes with `node scripts/release-notes.mjs vX.Y.Z /tmp/block-beaver-release-notes.md`. Keep any candidate status accurate until publication.
2. Run the complete CI matrix: Linux Node 22.18.0/22/24/26 and macOS/Windows Node 24, dependency audit and required security checks. Run the live editor gate including trusted native Codex hooks. Record exact commits and evidence in the release task; a successful run for an earlier commit is insufficient.
3. Run `npm pack --json --pack-destination /tmp/block-beaver-release` (create the destination first). Inspect the tarball and install it in a disposable target. Verify public exports, onboarding, regeneration and uninstall. Run `npm publish /tmp/block-beaver-release/block-beaver-X.Y.Z.tgz --dry-run --access public` to inspect the exact reviewed artifact without publishing.
4. After authorization, merge into protected `main` and confirm required checks pass at the release commit. Remove the candidate status paragraph from the changelog and update the README’s unpublished/source-checkout language as part of the reviewed release change and regenerate the artifact if its bytes changed.
5. With an authenticated npm account authorized for `block-beaver`, publish the reviewed tarball using `npm publish /tmp/block-beaver-release/block-beaver-X.Y.Z.tgz --access public`. Complete npm's normal authentication/2FA requirements. Do not add registry credentials to repository files. Verify the registry version and integrity match the artifact before proceeding; a published name/version cannot be reused.
6. Create and push an annotated `vX.Y.Z` tag at that same release commit. The release workflow validates the package version, changelog and main ancestry, reruns checks, then creates the GitHub release. Never move a published tag. A failure requires investigation rather than assuming npm and GitHub publication happened together.
7. Verify registry installation in a fresh target, the GitHub release/downloads, badges, Pages site and security reporting route. Record corrections in a patch release. Teacake adoption should pin the verified version and review `install --dry-run` before installation.

The CLI requires Node.js 22.18+; Node 24 and 26 are checked too. Known graph and host-integration limits are recorded in the [changelog](../CHANGELOG.md) and the release verification task. npm and GitHub releases are separate operations; the existing workflow deliberately contains no npm credentials or automatic npm publication.

The tarball, dry-run and immutable-version semantics follow the official [npm publish documentation](https://docs.npmjs.com/cli/v10/commands/npm-publish/). A future automated npm publisher should use a separately reviewed authentication setup; it is not required to install the reviewed candidate tarball locally.
